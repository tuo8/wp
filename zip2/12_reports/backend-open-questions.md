# 存储后端 · 未决问题清单（Open Questions）

> 每一项都写清四件事：**现在知道什么 / 为什么还不能定论 / 需要哪一种服务端证据 / 能否合法取得**。
> 凡是外部不可得的，本轮不留"猜测性结论"，只留缺口。
> 本轮**明确未做**：端口扫描、越权访问、绕过认证、修改他人对象、破解客户端。

---

## Q1 底层介质是「文件系统块库」还是「对象存储」还是「分布式 KV」？

- **已知**：对外是一个自研块服务，`/ipfs/blocks/{1位hex}/{2位hex}/{cid}`，按 CID 返回 4 MiB 不可变块，逐块可校验，404/400 由源站程序生成。
- **为什么不能定论**：四种实现（本地盘目录、DFS 目录、对象存储 key 前缀、KV 桶前缀）都能映射出**完全相同**的 URL 形状。对象存储被前置代理包一层后，响应头里的 `x-amz-*` / `x-oss-*` / `x-cos-*` / `x-bce-*` 会被吃掉——本轮这些头 0 命中，既不能证明"不是"，也不能证明"是"。
- **需要的证据**：块库侧的一次目录/对象列举（哪怕一条），或对象存储的错误码/请求 ID 格式，或块服务的部署清单。
- **合法性**：需服务端授权。外部不可得 ⇒ 本条只能停在 `UNKNOWN`。

## Q2 两级 16 进制扇出（`/2/68/`）是否对应真实目录树？

- **已知**：`2` 与 `68` 取自 multihash 摘要的前缀；807 个块的路径前缀分布随 CID 均匀散开。
- **为什么不能定论**：扇出到两级是**内容寻址库的通用做法**（避免单目录条目过多）。它既可能是 `mkdir 2/68`，也可能只是 key 前 3 个字符的字符串切片。
- **需要的证据**：一次 `ls`/`find` 的输出，或对象存储 list 的分隔符行为（若 `delimiter=/` 返回 CommonPrefixes 则倾向真实目录语义，若纯前缀匹配则不是）。
- **合法性**：需服务端授权。外部不可得。

## Q3 是否接入（私有或公共）IPFS swarm？

- **已知**：数据模型与 IPFS/UnixFS 字节级一致（根节点 41 973 B 离线复算 CID 完全吻合）；但对外端点、错误体、XOR 层都不是 Kubo/Boxo 默认行为；`delegated-ipfs.dev` 对三个自有 CID 返回空 provider 列表（16 B），对照 CID 返回 30 432 B。
- **为什么不能定论**：空 provider 至少有四种解释——节点不公告、节点离线、路由服务视角差异、私有 swarm。反过来说，"用 go-ipfs 的 DAG 库组装、但不跑 swarm"是完全可以实现的，从外部无法区分。
- **需要的证据**：① 对同一 CID 用 2–3 个独立路由服务（`delegated-ipfs.dev`、`cid.contact`、自建 Kubo `routing findprovs`）在不同时段各查 3 次以上；② 若服务端曾返回过 `peer_id`/`multiaddr`（本轮 0 命中），即可直接判定。
- **合法性**：① 可做，本轮只做了单源单次；② 需服务端泄露，不可强求。

## Q4 `pic01–04.hhhtcu` 的确切角色、容量与选路规则？

- **已知**：仅在中国出口路径出现，位于 `via` **尾部**，4 个实例负载近似均分（211/207/200/189）；美国出口 24 次采样 0 次出现。
- **为什么不能定论**：`via` 只能证明"它在链上哪一侧"，不能证明它是缓存、是四层转发、还是取流网关；也无法判断它的容量与是否持有数据。
- **需要的证据**：① 该名称的 DNS/A 记录（内部域名，外部不可解析）；② 服务端拓扑；③ 从第三个、第四个地理位置（如欧洲、华南）再采样，看它是否随区域更换命名。
- **合法性**：③ 可做（需多地出口）；①② 不可得。

## Q5 真实源站节点数量、地理分布、是否独立集群？

- **已知**：只有 `via` 链，且链在源站侧不存在（`via` 是 CDN 层自述，源站一般不写入）。
- **为什么不能定论**：CDN 的 `via` 终止于"最后一层缓存/回源代理"，其后是回源专线，没有可观测跳。
- **需要的证据**：源站 IP 清单与拓扑；或回源请求的 `X-Forwarded-For` / trace id 对应关系（本轮 `x-request-id` 只到 CDN 层）。
- **合法性**：需服务端授权；端口扫描属越权，**不做**。

## Q6 副本因子、纠删码、跨可用区容灾？

- **已知**：块尺寸恒定 4 MiB，末块为余数；未见 parity/校验片对象；单对象读取成功率 807/807。
- **为什么不能定论**：副本与 EC 是**存储层内部策略**，对外完全透明。4 MiB 恒定也可能发生在 3 副本实现上。
- **需要的证据**：集群配置、`replication factor`、EC 参数（k/m）、机架拓扑；或人为下线一个节点观察读失败率（属破坏性测试，**不做**）。
- **合法性**：均需服务端侧信息。

## Q7 删除后的垃圾回收窗口与判定条件？

- **已知**：删除 3790 s（63 min）后，根与叶子用**新地址 + 新 auth_key** 仍可取且全链 MISS；用已删 `content_identity` 直接 `Create` 在 898 ms 内成功重建记录（未上传任何块）。
- **为什么不能定论**：只能给出**下界 ≥63 min**。GC 可能按时间（如 24 h/7 d）、按引用计数、按容量水位，或根本不删（只删元数据）。
- **需要的证据**：更长窗口的复读（24 h / 7 d），以及"同一 CID 是否对其他账号可秒传"。前者可做但因额度与时间受限；后者属跨账号探测，**不做**。
- **建议**：若继续，用最小成本方式——每天固定时刻读 1 个 165 B 的根块，连续 7 天，记录 `age`/HTTP。

## Q8 去重（秒传）的作用域是「账号内」还是「全局」？

- **已知**：同账号内同 `content_identity` 秒传 83–898 ms 成功；`CreateUploadTask` 对已存在内容不会返回已存块列表。
- **为什么不能定论**：需要第二个账号上传同样内容来判断是否命中他人已存块——这既涉及他人数据边界，也需要注册新账号，**本轮不做**。
- **需要的证据**：跨账号实验（需合规前提与账号方授权）。

## Q9 整文件网关的缓存策略与播放路径的实际命中率？

- **已知**：`gateway_head` 观测到 `x-response-cache: parent_hit`、`age: 2875`；`last-modified` 固定为 `1989-06-04 15:04:05`；`etag` = 根 CID；Range 返回 206。
- **为什么不能定论**：2875 s 是**某一次**观测到的年龄，不等于 TTL；播放时是否总命中父层缓存，取决于 URL（`/file/{cid}/{uid}/{name}`）是否含会变化的参数。
- **需要的证据**：同一 URL 连续多日 HEAD，记录 `age` 是否被重置；或对比不同 `uid` 的同一 CID 的命中情况。
- **合法性**：可做，成本低。本轮未做，列为后续项。

## Q10 `store_type` 是否在其它客户端版本中启用？

- **已知**：当前 Web 客户端（`202603182100`）中 `storeType` 只影响"是否跳过 CID 校验"，服务端不返回该字段；APK 1.0.24 的 `libapp.so` 中未见同等分支证据（仅见 gRPC 方法名）。
- **为什么不能定论**：协议字段可能保留但未启用；也可能在更高版本服务端启用。
- **需要的证据**：更新版本客户端的前端包差异对比，或服务端 proto 定义。
- **合法性**：公开前端包对比可做；proto 不可得。

## Q11 上传入口与下载入口共用一组 IP（101.72.219.x）——是同一集群还是同一四层？

- **已知**：`simple-file-proxy.2dland.cn` 与 `ipfs-gateway.qzy.xyz` 解析到同一批 IP；`slices.qzy.xyz` 用另一批（116.136.20.227/228）。
- **为什么不能定论**：同一组 VIP 可能是同一个七层网关按 Host 分流，也可能是四层 LB 后接不同后端。
- **需要的证据**：TLS 证书 SAN 差异（已看到：`*.2dland.cn` vs `*.qzy.xyz`，说明**证书不同但 IP 相同** ⇒ 至少是同一四层、按 SNI 分流）；后端归属仍需服务端信息。
- **说明**：本条已有部分结论（同一四层、SNI 分流），列此仅为标注"后端是否同机"仍未决。
